# Run 运行快照、冷热事件与有界回放

2026-09-01。通用安全智能体底座能力；不增加具体场景、UI、账号或租户。它保存原始运行事实，不使用模型摘要代替证据。

## 保存什么、改变什么

`scenario_events` 的 Run ID、sequence、command ID、event index、event type 和时间索引始终保留；`scenario_commands` 的请求指纹与结果 revision 不删除。
受控归档把一个连续前缀范围的原始事件行压缩保存到 `scenario_history_segments`，并将原表正文改成对应段的引用。起始事件正文继续保留热副本，供既有固定 scope 查找使用；归档段也保存其原件和摘要。
因此这是**同一 SQLite 内的正文分层与压缩**，不是独立冷对象库、数据库备份或数据删除。SQLite 文件大小不保证立即缩小，物理维护继续使用既有独立授权流程。

每段还保存该段末尾 revision 的通用 Run 状态快照，包括包绑定、授权引用、Work/审批/输出/证据引用和检查点引用。快照通过 Core 的纯事件归约生成，不调用场景工厂、策略、输出验证器或模型。
格式和归约器版本当前均为 1；后续改变归约语义时必须明确更新兼容策略，不能把旧快照盲目当成新状态。
快照正文、原始事件正文、压缩字节、起始事件及相邻段关系均记录摘要。归档段和审计不能更新或删除，已归档事件元数据与命令也受永久索引保护。
摘要用于检测缺损/不一致，不是抵御有权修改整个数据库及触发器的宿主的数字签名证明。

## 运行和查证链路

Core 的 EventStore 契约增加可选的 `loadState`、`hasUsedLease` 与 `validateState`，保留无快照宿主的完整事件回放兼容路径；Core 不引入 SQLite、压缩库或具体场景。
生产 SQLite Adapter 使用最近的可用快照，再按有界批次归约后续事件。启动新 Run 和执行命令时在提交前检查状态容量，正常 Runtime 仍检查当前包信任，快照不发放权限。

当前状态读取检查事件序号连续性、归档段链、全部压缩段字节摘要、热引用覆盖、起始事件、所选快照格式/摘要/身份、尾部事件以及当前 Run 投影。
档案缺段、压缩字节损坏、快照失效或绑定不一致均拒绝；不使用空记录，不自动降级到猜测状态。
只读取证可以独立按原 sequence 查看仍完整的事件页，不要求旧包重新受信；这不意味着其他缺损范围已经恢复。

已接通的读取者包括：

- 正常 Durable Runtime、新宿主恢复、独立旧任务取证/停止和按任意旧 revision 回放。
- 固定授权兼容升级、执行历史归档检查和存储维护中的 Run 状态读取。
- Planner/Observer 的有界近期事件输入、提交后事件发布和共享审计缺项补记。
- 命令重放：同一命令的事件可跨冷热边界回读，校验原序号、event index 和身份，不重复追加事实。

租约防重用不再依赖加载完整历史。新的 `work_claimed` 与永久 `scenario_lease_history` 在同一事务提交；旧记录在归档事务中明确补入索引。
已归档 claim 缺少索引时拒绝回放，重复的旧 lease 身份不能通过搬走正文而重新变成“没用过”。

## 受控归档接口

Foundation 默认注册受管理能力通道保护的以下入口；匿名和 Worker 通道不可使用：

- `GET /api/scenarios/runs/:runId/history?caseId=…`：段范围、字节数、归档位置与全库容量使用。它是元数据清单，不宣称已经完成一次全面介质检查。
- `POST …/history/preview`：caseId、expectedRevision、throughRevision；仅检查本次连续范围，返回 planFingerprint，不写快照或归档。
- `POST …/history/archive`：追加 commandId、actor、reason、planFingerprint，执行独立授权及原子归档。
- `GET …/history/audit?caseId=…&commandId=…`：核对操作审计摘要、Run/Case、原段身份并回读；真正的档案正文验证由冷热读取器完成。

可信宿主显式提供 `SecurityAgentFoundationOptions.historyArchiveAuthorizer.authorize(request)`，缺失默认拒绝。
允许结果必须包含非空 authorizationRef 和未来 expiresAt，授权等待最多 10 秒。actor 是本人操作说明，不是用户账号或授权依据。
请求先固定副本；事务内重查 revision、连续范围、前段身份和原始行摘要。并发追加或另一次归档改变计划时冲突，不默默换范围。
同 commandId 同请求每次仍需授权，再回读原审计；不同正文冲突。归档不改变 Run revision、生命周期、scope 或包信任，也不会触发工具重试、续跑或占用释放。

压缩段、末尾状态快照、旧租约索引、热引用、容量计数和审计在同一个 SQLite 事务中提交。中断、满额或任一步写入失败全部回滚；进程重启不会留下半搬走的正文。
没有启动时自动归档、自动授权或根据容量偷偷删除事件。长任务部署需要提前配置可信归档授权，并按需推进前缀；未配置授权不能绕过容量门禁。

## 长历史与容量边界

- 每次归档 1–1,000 个连续事件，原始段和解压输出最多 16 MiB，压缩段最多 16 MiB；状态最多 2 MiB、包含头部的快照最多 2.0625 MiB。
- 单 Run 最多 1,024 段。全库默认 100,000 段、1 GiB（压缩字节、快照和保守元数据开销之和）；审计最多 50,000 条、单条 8 KiB。
- 写入使用现有 recovery 物理余量准入，计入原正文替换、压缩档案和快照的保守开销；不会因为压缩后较小就跳过 WAL/磁盘检查。
- 每次状态回放最多归约 5,000 条尾部事件、合计 16 MiB；可分批归档旧前缀后再处理更长历史。此前超过 5,000 条的 Run 不必先整体回放，就能按 1,000 条前缀逐段迁入快照。
- 通用事件读取每批最多 1,000 条/16 MiB；兼容完整导出最多 5,000 条/16 MiB，超过需分页。处置对外事件页仍最多 100 条/4 MiB；内部读取单个压缩段可能解码最多 16 MiB。
- 原始状态本身过大、超大单事件、永久键增长及快照随 Work/输出数量增长仍有上限。快照不是缩减结构化事实；超限整体拒绝，不靠截断“成功恢复”。

当前快照节省的是反序列化和逐事件归约成本，不是把全历史 I/O 变成常数：每次状态读取仍扫描永久事件索引并逐段验证压缩字节。
验证按段进行，不同时展开整个历史；段越多仍有 I/O、CPU 和同步数据库占用成本。没有无限规模、异步流式解压、独立冷库或真实长稳性能验收。
恢复历史 revision 时选取不超过目标 revision 的快照并回读所需尾部；目标落在段内时从原始冷事件恢复，不近似取最近状态。

## 验证及下一步

本批新增 41 项集成回归，覆盖原事件/状态等价、超过原完整回放上限的历史、冷热命令重放、租约索引、包版本迁移、失信包只读取证、审计补记、生产路由、授权/竞态/容量和缺损拒绝。
压缩段写入、热引用替换、审计写入、提交后四个窗口真实 SIGKILL，各用两次新宿主回读；历史转存不自动恢复外部动作。
测试使用中性事件与可控模型替身，未调用真实模型，未运行暂缓的 24/72 小时长稳。

下一整批优先补齐底座的受控备份与灾难恢复：当前各类冷正文仍在同一个数据库内，单库损坏不能靠“已归档”恢复。
需明确数据库、外部文件与宿主密钥依赖的完整清单，在隔离位置验证恢复，并保留未知执行围栏；不自动覆盖运行中的库或恢复后直接重跑工具。
