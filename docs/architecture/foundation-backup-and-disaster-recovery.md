# 底座受控备份与灾难恢复

## 目的与边界

本能力保存通用安全智能体底座的持久事实，不包含任何具体漏洞、目标、协议或 Scenario 规则。它解决的是：活动 SQLite 损坏或旧宿主不可用时，在另一个目录恢复可核验的调查事实，同时阻止旧备份重新触发已经可能发生过的外部动作。

备份不是第二套执行授权，也不是宿主镜像。当前导出包含：

- 通过 SQLite Online Backup API 得到的一致数据库副本，包含提交在 WAL 中的页面以及同库冷正文；
- 可选的、由可信宿主逐项指定且预先固定 SHA-256 的不可变附件；
- 带数据库、Schema 和附件摘要的规范化 manifest；
- 明确的五类库外依赖缺口。

以下材料默认不放进备份：Vault 明文密钥、模型/MCP 凭据、审核或签名私钥、当前宿主的包装配信任、原生 helper 权限、Provider 工作目录和没有显式声明的外部文件。SQLite 中已有的加密密文会保留，但缺少原密钥时只能作为证据保留，不能声称凭据已恢复。

因此所有 manifest 固定为 `executionReady: false`。显式附件只证明这些字节被完整搬运，不能证明所有外部资料均已覆盖。

## 备份发布协议

备份根目录和恢复根目录由可信宿主配置，不接受 HTTP 请求传入路径；两者必须互不包含、非符号链接，并在 POSIX 下为私有的 `0700` 目录。操作标识只能使用有界安全字符，目标以排他方式新建，既不覆盖活动库，也不覆盖已有文件。

一次备份按下列顺序执行：

1. 管理通道接收固定请求，独立 authorizer 发放有截止时间的授权；
2. SQLite 中先写入不可变的 `started` 审计；
3. 新目录先写 `BACKUP_ONLY`，阻止直接把数据库副本当宿主启动；
4. Online Backup 把一个一致快照写入 `database.sqlite`，不直接复制活动库及其 WAL；
5. 附件使用 no-follow 文件描述符读取，复制时同时核对大小、摘要和截止时间；
6. 独立打开副本执行 `quick_check`、必需表/列兼容检查和 Schema 摘要检查；
7. 写入并 fsync manifest，随后持久化 `prepared` 审计；
8. 最后以 `READY = sha256(manifest)` 作为发布点，再写 `completed` 审计。

验证会重新核对 `READY`、manifest、允许的精确文件集合、每个文件的字节数/摘要、SQLite 完整性与 Schema 摘要。`-wal`、`-shm` 或其他未登记文件会导致拒绝。

相同命令标识会重新授权并核对原请求。完全相同且已经发布的请求只核验结果，不重做副本；同一标识对应不同请求会冲突。若崩溃发生在 `prepared` 之前，目录和审计保留为隔离证据，必须换新命令处理，系统不自动删除或猜测回滚成功。若发布已完成而最终审计中断，重启后可以核验现有发布并补记 `completed`，不会重复恢复。

## 隔离恢复与永久执行围栏

恢复要求另一次独立授权，还要求操作者把之前验证得到的 `backupId + manifestDigest` 明确固定在请求中。恢复仍写入新目录；源备份、活动库和已有目的地均不修改。

数据库与附件复制、复核完成后，恢复事务向数据库安装不可变的 `foundation_restore_fence`：

- 模式永久为 `inspection_only`；
- 记录备份、恢复和 manifest 身份；
- 明确 `automaticResume: false`、`externalCleanupCertified: false`；
- 表的插入、修改和删除均被触发器拒绝。

恢复目录在复制前已有 `RESTORE_PENDING`。没有围栏的中间副本即使数据库文件存在也无法通过 `createDb` 启动；有围栏的副本还必须同时存在匹配的 `READY` 和 manifest。恢复数据库以只读及 `query_only` 模式打开，启动路径在以下动作之前直接返回：

- 数据迁移和启动修复；
- Vault key 的读取或重新生成；
- MCP 连接和模型配置加载；
- Scenario 包装配、当前信任解释和授权派发；
- Execution Node、Provider、Worker、Planner、Observer 和调度器启动；
- model call 中断修复、reserved 占用释放、旧调用恢复或工具重放。

当前仍没有解除围栏或直接“激活恢复库”的 API。恢复宿主可以在独立可写审计库中逐项核对 Vault key、Scenario 材料、上下文资源、模型配置、MCP/Provider 配置和外部副作用，但核对完成只得到 `review_complete_but_locked`，不会修改恢复库、解除围栏或恢复执行。恢复执行只能另建候选工作库并走下述显式活动指针切换；不能修改这张表来绕过流程。

## 取证入口

恢复宿主只安装受管理通道保护的读取入口：

- 恢复身份和依赖缺口；
- Run 摘要分页；
- 经过历史段/快照完整性校验的 Run 状态和事件分页；
- Run 范围内的进程占用、Managed 占用和调用状态分页。

查询固定 scope、游标、页数和返回字节上限，不加载 Scenario 包或调用模型。未知占用、reserved 记录、活动 lease 和 uncertain invocation 保留原值；入口总是报告 `externalCleanupCertified: false`，不把“在旧快照里没看到”解释成真实世界中没有发生。

## 加密签名离线介质

已发布且重新核验通过的本地备份可以导出为 `traceforge.foundation-media.v1` 离线介质。介质正文使用 AES-256-GCM 独立分卷加密，分卷的介质身份、序号、原文件、偏移、密钥标识与密文摘要均绑定到认证数据；规范化 manifest 由可信宿主持有的 Ed25519 私钥签名。私钥和对称密钥不写入介质、数据库、HTTP 返回或审计正文。

介质复制到独立存储后，只需固定的 manifest digest 和当前未撤销的签名公钥即可在不访问原备份控制库、也不持有解密密钥的情况下核验来源、精确文件集、分卷布局和密文字节。导入时才要求可信宿主提供匹配的解密密钥；文件只会重建到新的 `BACKUP_ONLY` 目录，并再次经过普通备份的 manifest、SQLite、Schema、附件和精确文件集验证，全部通过后才发布新的 `READY`。错误密钥、损坏分卷、签名或 manifest 篡改、过期/撤销签发者、未知文件和发布中断都保持隔离，不能启动。

默认分卷为 4 MiB，单卷硬上限 16 MiB；默认单介质最多 16 GiB，硬上限 64 GiB；条目、分卷、操作时限和介质根目录均有固定上限。签名只证明介质来自受信签发者且字节未变，不负责向新宿主分发对称密钥；密钥托管、轮换、异地保管和恢复演练仍是部署责任。

## 保留、法证冻结与精确销毁

所有本地备份和离线介质默认处于 `forensic_hold`，不会因目录数量或磁盘压力自动删除。解除保留、重新冻结和销毁都是独立命令：每次调用及幂等重放都重新授权，销毁还必须先生成固定 revision、目标身份、精确文件清单和指纹的预览，再由另一显式操作执行。审计、操作和逐步销毁记录不可变。

销毁只遍历验证时固定的已知文件，不使用递归删除；根目录或文件被替换为符号链接、目标内容在预览后变化、出现未知残留时一律拒绝并保留现场。中断恢复只继续已持久化的精确删除计划；文件已经删除但最终审计失败时，重放只补记完成，不把相邻目录或后来出现的文件当作原目标。这里的“销毁”是文件系统级精确删除，不声称 SSD、快照、备份服务或底层介质上的字节已安全擦除。

隔离残留会出现在库存中并标记为 `quarantined` 或 `published_unverified`，但不会被自动当作垃圾。超大库存和审计也受物理空间、条目、正文和时间上限约束，满额时拒绝新操作，不以删除旧证据换取可用性。

## 恢复激活前核对

恢复依赖核对只写独立宿主审计库，明确禁止把只读恢复数据库兼作核对账本。六类依赖分别由可信宿主 verifier 提供有期限、带材料指纹的结构化证明；当前材料指纹变化会使旧证明变成 `stale`，过期、撤销、阻断和未提供分别保留为 `expired`、`revoked`、`blocked`、`pending`。

外部副作用项还会读取恢复库中的事实：只要存在活动 lease、进程或 Managed 占用、uncertain invocation、运行中的模型调用或准入记录，就自动阻断，不能由一条笼统的“已检查”覆盖。命令幂等重放仍会重新授权，冲突请求拒绝，证明与审计在同一事务提交。所有依赖满足也只表示人工复核材料齐全；核对协议固定 `activationSupported=false`、`fenceRemains=true`、`executionReady=false`，没有 activate/unfence 路由。候选库控制面消费完整核对快照，但不是核对接口的隐藏解锁分支。

## 候选工作库与人工切换

候选库只能从已发布的只读取证恢复创建，源恢复文件和围栏字节不修改。创建请求固定完整 readiness digest，并让可信宿主对六类当前材料分别重新装配；装配只保存材料指纹和有界引用，不把 Vault、模型或 MCP 凭据写进候选 manifest、审计或 HTTP。任一材料缺失、过期、指纹变化或外部副作用未核实时，候选不能发布。

数据库复制到独立私有目录后，才在这份副本内移除复制来的围栏，并写入不可变的来源 provenance 和候选 guard。所有原来仍为 running 的 Run 通过正常事件链追加 `run_paused`，不是直接改投影；已暂停、已取消和已完成状态保持。附件按恢复 manifest 精确复制和复核。最后发布 `candidate.json + READY + CANDIDATE_ONLY`，中断残留保持隔离。

`CANDIDATE_ONLY` 永久保留，因此直接把候选 `database.sqlite` 传给 `createDb` 仍会拒绝。激活必须先根据候选 revision、当前 pointer generation、当前材料指纹和来源 provenance 生成 plan fingerprint，再经独立授权写入审计中的 `switch_prepared`；原子替换可信宿主 `ACTIVE.json` 是唯一切换点。生产 `main` 在任何模型、MCP、Provider、Execution Node 或数据库迁移之前解析活动指针，并同时核对目录身份、候选发布、当前六类材料指纹和数据库内 guard，随后才允许候选以普通可写宿主启动。

切换不会自动 resume 旧 Run，也不重放工具动作；操作者以后必须沿现有 Run 授权入口逐项显式恢复。回退使用同样的预览、revision/generation 固定、独立授权和原子指针协议，而且只能回到紧邻的前一个活动候选，不修改法证恢复库或把任意路径塞进 pointer。切换前中断不改变活动库；指针已切换但最终审计中断时，幂等重放重新授权、核对同一计划并只补记审计，不再次切换。

活动指针与候选文件由可信宿主目录保护，不声称能抵抗拥有同一 OS 账号写权限的攻击者。当前装配 callback 是宿主必须实现的信任端口，不自动复制秘密，也不证明外部服务真的长期可用。候选发布数量、单库字节、命令、审计和操作时限均有上限；真实断电、跨文件系统 rename 语义和 Windows 权限仍须实机验收。

## 容量、保留与部署责任

默认单次最多 8 GiB、32 个目录、目的卷至少保留 64 MiB，操作合作式截止 60 秒；硬上限为单次 64 GiB、1,024 个目录、128 个附件和 5 分钟。创建前检查预计字节与空闲空间，Online Backup 期间继续检查页面增长和空闲空间。SQLite 原生完整性检查本身不能在执行中间强制取消，超大库仍需部署方安排维护窗口。

系统仍不自动删除备份、介质或失败残留。完整发布和隔离残留都计入目录数量；可信宿主可以通过上述法证保留和精确销毁协议处理明确目标，但权限继承、磁盘快照、底层安全擦除和离线介质的实际异地保管仍由部署策略负责。目录与可复制介质不等于多节点一致性，也不能抵抗拥有同一 OS 账号和密钥的攻击者篡改或删除全部副本。

当前测试覆盖活动 WAL、冷历史、加密密文、明确附件、新控制库/新宿主、摘要/格式/sidecar/路径/容量/授权错误、只读与 scope 门禁、旧占用保留、幂等、持久审计、离线分卷/签名/独立导入、保留与精确销毁、依赖核对、候选来源/装配/暂停/直接启动拒绝、生产 main 活动指针启动、双候选回退，以及备份、恢复、介质和候选切换的真实 SIGKILL 窗口。真实断电、真实可拔插或异地存储、密钥恢复/轮换演练、安全擦除以及 Windows 文件权限继承仍是部署验收项。
